# Security Hardening Audit, 2026-10

Repository: `omkhar/workcell`

Baseline: release `v1.0.2` and the default branch at the time of the audit.

Status: Seven hardening changes are merged.
Three findings remain open.
Workcell publishes this record without a security advisory.

## Scope

The audit is the X1 baseline audit.
It covered the launcher on the host, credential injection, the container boundary, and egress controls.
It also covered the agent control plane, the audit trail, state on the host, and the CI supply chain.

## Method

The audit used eight review lenses.
The lenses are launcher, credentials, container boundary, egress, agent control plane, audit integrity, host state, and CI supply chain.

Each lens produced candidate findings.
A second reviewer tried to disprove each candidate with source analysis and a replay.
Only findings that survived this step are in the record.
The audit found 13 confirmed findings.
Some findings describe the same defect, so the record groups them into 10 items.

Codex reviewed each fix before merge.
Each fix includes a regression test.

## Threat model

The attacker is the agent in the container, or repository content that drives the agent.
The attacker does not control the operator-owned Workcell state root.
The attacker cannot replace the VM and container boundary.

## Fixed findings

### X1-01 Session capture through `docker cp`

Severity: Medium.
Fixed in: PR #750.

The launcher copied two agent-writable files from the container with `docker cp`.
The files are the file-trace log and the session audit state.
The copy did not reject a symbolic link in the container source.
The launcher then ran `chmod` on the host destination.
An agent could plant a link, and the `chmod` then changed the mode of an operator file.
The trace log also lost its evidence value.

The fix copies into a private directory and accepts only a regular file.
It sets the mode there and renames the file over the destination.
A rename replaces a link and does not follow it.

Residual risk: The agent can still write false content into the trace log.
The launcher treats that content as untrusted.

### X1-02 SSH config safety check

Severity: Medium.
Fixed in: PR #743.

The SSH config parser split directives on white space only.
OpenSSH also accepts `Keyword=value` and quoted keywords.
A config in that form passed the safety check.
Workcell then labeled the session `safe`.
A second defect skipped SSH sources in the workspace check.
The check covered the credentials table but not SSH config, known hosts, or identities.

The fix parses the keyword as OpenSSH does.
It also rejects SSH sources that are inside the workspace.

Residual risk: The check is a deny list of risky directives.
An operator can still accept a risky config with `allow_unsafe_config`.

### X1-03 Egress allowlist replacement

Severity: Medium.
Fixed in: PR #746.

Each apply of the allowlist removed the old chain before it built the new chain.
For a short time, no default-deny rule covered running containers in the profile.
A connection that opened in that time stayed open.
The `ESTABLISHED,RELATED` rule kept it open for the rest of the session.

The fix resolves all endpoints first.
It then replaces each chain in one `iptables-restore --noflush` transaction.
The new chain ends with the default-deny rule.

Residual risk: Concurrent sessions in one profile still need the same endpoint set.
`docs/threat-model.md` states this limit.

### X1-04 Codex `projects` override guard

Severity: Medium.
Fixed in: PR #742.

The guard for Codex `-c` overrides did not list the `projects` table.
A `-c` override of `projects."<path>".trust_level` made Codex trust the project.
A file that the agent wrote in `.codex/config.toml` could then set guarded keys.

The fix adds the `projects` table to the guarded keys.
It covers the `-c`, `--config=`, short-form, and inline-table forms.

Residual risk: The guard is a deny list.
Codex can add new keys, and the guard needs an update for each one.

### X1-05 Provider managed settings scope

Severity: Medium.
Fixed in: PR #751.

Workcell wrote the Codex `requirements.toml` and `managed_config.toml` in `$CODEX_HOME`.
The pinned Codex version does not read these files from that path on Linux.
The administrator layer was absent.
Workcell wrote the Gemini baseline settings at user scope.
A repository `.gemini/settings.json` file could override them.
A workspace `.env` file could shadow the managed `.env` file.

The fix installs the Codex requirements file and the Gemini system settings at provider system scope.
The files are root-owned and read-only.

Residual risk: Provider versions control the path they read.
A provider upgrade needs a check of the system-scope paths.

### X1-06 Vendored Rust crate integrity

Severity: Low.
Fixed in: PR #745.

The `libc` crate in the vendor tree builds the execution guard.
The checksum data in the vendor tree vouches only for the vendored files.
A change to a vendored file with a new checksum built without error.
`docs/ci-threat-model.md` claimed a control that did not bind the bytes.

The fix adds a CI check.
The check compares the vendor tree with crates.io for the locked versions.
The document now states the real control.

Residual risk: A change that passes the single code owner is still a known gap.
`docs/ci-threat-model.md` records this gap.

### X1-07 Session log read race

Severity: Low.
Fixed in: PR #740.

`session logs` checked the log path for links and then opened it with `os.Open`.
`os.Open` follows links.
An agent could swap the path between the check and the open.
This needs a log path that the operator placed inside the workspace.

The fix opens the file with no-follow semantics and checks that it is a regular file.

Residual risk: None known for this path.

## Open findings

These findings are not fixed.
Each one is a hardening gap that does not cross the VM and container boundary.

### X1-08 Readonly session-property files

Severity: Medium.
Fixed in: Not fixed.

In `readonly` mode, the agent owns the `/run/workcell` tmpfs.
The provider wrappers trust the session-property files in that directory.
They trust these files over the environment of process 1.
The agent can write these files and start a provider.
The new provider run then uses a weaker autonomy or profile value.
The mode stays at or below `build`, and `breakglass` is not possible.

The running provider keeps its flags.

Residual risk: An agent can lower its own session controls for later provider launches.
The `--agent-autonomy prompt` setting is an explicit lower-assurance choice.
The planned fix gives the environment of process 1 precedence over the files.

### X1-09 Git `commondir` mask gap

Severity: Low.
Fixed in: Not fixed.

The in-container Git mask covers hooks, config, worktrees, and modules.
It does not cover `.git/commondir`.
An agent can point `commondir` at a directory with its own config and hooks.
Git inside the container then runs those hooks.
The agent can already run any code in the container, so this gives no new privilege.
Host Git calls use the safe wrapper and do not run the hooks.

Residual risk: The mask is weaker than `docs/invariants.md` and `docs/owasp-agentic-mapping.md` imply.
The planned fix masks `commondir` and updates both documents.

### X1-10 Audit digest NUL ambiguity

Severity: Medium.
Fixed in: Not fixed.

The audit digest joins record fields with a NUL byte.
The strict decoder accepts a NUL byte inside a value.
A party that can write the audit log can merge two fields into one.
The digest input stays the same, so the chain and the seal still verify.

The attacker needs write access to the log and not the signing key.
By default, both are in the same state root, and a log writer can usually re-sign.
The attack can merge only adjacent fields and cannot add bytes.

Residual risk: `session verify` can report `verified` for a restructured record.
The planned fix rejects NUL bytes in the shared strict decoder.
